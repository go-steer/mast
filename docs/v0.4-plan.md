## 0. The re-cut, and why

v0.3's §5 said **v0.4 = M4 + M5**: unattended monitoring with in-Slack approvals (M4 = W4 + W5 + W6) plus the change-set work (M5 = W7.0 + W7 + W8). Taking that literally makes v0.4's ship date a function of two other repos' schedules — [`k8s-lookout`](https://github.com/go-steer/k8s-lookout) has to land W5's finding-state surface and [`switchboard`](https://github.com/go-steer/switchboard) has to land W6's interactive events before four of M4's six tasks can even be written.

That is precisely the reasoning that produced the M1–M3 cut for v0.3, applied one release later. So:

- **v0.4 = mast only.** M5 in full (W7.0, W7, W8) plus the two W4 tasks that need nothing outside this repo (W4.1, W4.3) plus the one J-tier test v0.3 identified and could not write (W0.6). Six tasks, one repo, no external dependency. *(Seven as of 2026-08-15: W4.3's `tier:` question promoted **W1.1a** into the release — §3.)*
- **v0.5 = parity.** W4.2, W4.4, W4.5, W4.6 + W5 + W6 — the tasks whose halves live in lookout and switchboard.

The demonstrable claim for v0.4: **"an operator approves the exact call that will fire, the loop runs on a schedule without an orchestrator, and every verdict becomes a labelled eval row."** That is a coherent release on its own, and it is the half that has to be true before unattended monitoring is safe to point at a cluster — the same ordering argument v0.3 made about the gate.

**M4 splits rather than being renumbered**, so nothing already written has to be re-read against new IDs:

| M | Contents | Release | Demonstrable claim |
|---|---|---|---|
| M4a | W4.1 + W4.3 + W0.6 | **v0.4** | "a bundle wakes on a schedule, spends one model call doing it, and the tier it spent it on is priced at that tier" |

| M5 | W7.0 + W7 + W8 | **v0.4** | "the operator approves the object that fires, and the verdict is training data" |

## 2. Test strategy — one new tier, and two corrections

[`./v0.3-plan.md`](./v0.3-plan.md) §2's S/U/E/J table and its inherited UAT conventions (credential-free, real SQLite across restarts, `${TMPDIR:-/tmp}`, `set -euo pipefail` + `trap cleanup EXIT`, bounded `wait_for`, wired into `all.sh` *and* `.github/workflows/ci.yml`) hold verbatim for the four tiers already there.

**This section originally said v0.4 adds no new tier. W7 made that false, and the honest correction is a fifth tier rather than a widened U:**

| Tier | What it proves | Provider | Cost | Cadence | Harness |
|---|---|---|---|---|---|
| **C — cluster** | mast's guarantees hold against a real API server, not a fixture standing in for one | `toolactor` (no provider, no credentials) | a kind cluster, ~2 min | on demand; pre-release for anything touching the gate | `scripts/live-kind-v0.4.sh` |

Why it is not tier U: U is credential-free *and* dependency-free, runs on every PR, and gates the build. C needs a container runtime, takes minutes, and **writes to a Kubernetes cluster** — so it is opt-in (`MAST_LIVE_KIND=1`), it is deliberately *not* in `dev/ci/presubmits/e2e.sh`, and it is not a gate. Why it exists at all: two of W7's claims are untestable offline. A precondition declared over a real read tool has to be right about a JSON shape mast does not control (finding (c)), and "the cluster moved" means *somebody else ran `kubectl scale`*, which a harness writing its own fixture file cannot honestly stage.

Its isolation is mechanical, and it is lifted from the sibling `core-sre-agent`'s `internal/kindcluster` (`github.com/go-steer/core-sre-agent`, not yet published) — which arrived at the same four guards for the same reason, under the rule *fault injection must never touch a real cluster*: the cluster is created by the script and named `mast-live-<pid>`; an existing cluster of that name is refused rather than adopted; kind writes to a kubeconfig under `${TMPDIR}` that must not already exist (kind *merges*); and after create the kubeconfig is verified to describe **exactly one** context, which is the check that makes the rest redundant. Every `kubectl` passes `--kubeconfig` and `--context` from an environment with `KUBECONFIG` unset, in the script and in `testdata/live/kubemcp` alike. The ambient `current-context` is never resolved on any path, and the MCP server refuses to start against a context without the `kind-mast-live-` prefix — the binary holding the write does its own checking rather than trusting its caller.

Two things the v0.3 plan got wrong that this release has to fix rather than inherit:

- **A new script, not a bigger one.** W1.4 finding (d) settled that each release gets its own acceptance harness and `dev/ci/presubmits/e2e.sh` runs them in order. So v0.4's UAT legs land in **`scripts/uat-v0.4.sh`**, run after `uat-v0.2.sh` and `uat-v0.3.sh`, failing on any. The v0.3 script is not grown; its 29+ assertions stay separately re-runnable as v0.3's acceptance pass.
- **`E-cost-tier` is misnamed.** §2 says tests carry their tier prefix (`U-gate-crash`, `E-approval-edited`, `J-severity-accuracy`) and W1.2 finding (b) established this test cannot live in the E tier at all. It is **`J-cost-tier`** from here on. ✅ Corrected in row 1 and W1.1's stanza by W0.6(a); the v0.3 findings that named it `E-cost-tier` keep the old spelling, because they record what was believed when they were written.

## 3. Workstreams

Format is v0.3's: **what**, **where**, **done when**, **test**. `→` marks the scoreboard rows it flips. Tasks are PR-sized.

### W7.0 — The change-set producer *(the long pole; blocks W7)*

✅ **Shipped 2026-08-15.** A finding now carries the call. `pkg/approval/changeset.go` is the new home of the contract — `ProposedChange`, the `proposed_change` field name, the normalized `(tool, arguments)` `Signature`, and a `ChangeSetChecker` that resolves each named tool's *declared* input schema and validates the arguments against it. The check runs as a before-tool callback on `finish_task`, so a report naming a tool the workload does not declare, or arguments that tool would reject, comes back to the specialist as `{"error": "invalid_proposed_change", ...}` and it gets to correct itself rather than the run failing. An accepted change set is recorded under a durable per-specialist state key, and `pkg/graph/graph.go` turns that record into the structural predicate: a finding with a non-empty recorded change set, whose verdict the operator approved, routes to the `change-executor` node, which is handed the approved calls verbatim. Everything fails closed — no schema resolver means every proposed change is refused, an empty or absent list leaves the finding exactly as it was, and a roster with more than one change executor turns the handoff off rather than guessing (finding (d)).

**What.** `finding.json` gains `proposed_change`: a typed, possibly-empty list of `{tool, arguments}` entries drawn from the workload's own `tool_catalog`, each validated against the named tool's declared input schema at the moment the finding is returned. A diagnoser that cannot name a machine-executable change returns an empty list and says why in `escalate` — the honest outcome for *"raise the memory limit, but I don't know to what."* The full argument is in [`./v0.3-plan.md`](./v0.3-plan.md) §3 W7.0 and in W2 finding (c), which is the live-cluster run that discovered the hole; it is not re-argued here.

**Where.**

- `examples/workloads/gke-triage/schemas/finding.json` — today `recommended_actions` is `{"type":"array","items":{"type":"string"}}`, i.e. prose addressed to a human. `proposed_change` sits beside it; `recommended_actions` stays, because the two answer different questions ("what should happen" vs "what call makes it happen") and an empty proposal still needs prose. Mirror into `deploy/base/config/` — `deploy/projection_test.go` pins the two trees byte-identical and will fail if you don't.
- `pkg/approval/edit.go` — **`normalizeEdit` is the validator to reuse, and it is not currently callable.** It is unexported and takes its schema off a `declarer` assertion on a live `tool.Tool`, because W2.5 only ever needed to validate an operator's edit against the tool ADK was about to run. W7.0 needs the same check keyed by tool *name* against the workload's catalog, one step earlier and with no tool instance in hand. Lift it to an exported, tool-instance-free entry point and have W2.5's path call the same code — two validators that can disagree about what "schema-valid arguments" means is the defect this task exists to prevent.
- `pkg/graph/graph.go` (`Build`) — the diagnoser→executor edge becomes a **structural predicate**: *finding carries a non-empty `proposed_change` ∧ the operator's verdict approved it → `change-executor`*. Specialist nodes are terminal today (W2 finding (c)); this is the one place that changes. Read [`./spike-findings.md`](./spike-findings.md) on the resume contract before touching the topology, and note W2.1's asymmetry: under graph dispatch a confirmation resume re-enters at START and upstream nodes genuinely re-execute, so the predicate has to be evaluated from durable state, not from a variable that survived the first pass.
- `pkg/workload/bundle.go` — the `tool_catalog` is already the classification surface (W2.2/W2.4); `proposed_change` validation reads it. No schema change expected there, which is worth confirming early rather than discovering late.

**Done when.** A diagnosis specialist returns a finding whose `proposed_change` names a tool in the catalog with schema-valid arguments; the executor runs **that** call and no other, or runs nothing when the list is empty; a finding whose `proposed_change` names an unknown tool or invalid arguments is rejected back to the specialist rather than passed on. — **met 2026-08-15**, all three clauses, and the middle one end to end: the operator approves `apply_change({"replicas":2})` and `replicas=2` is what the tool's own ledger records.

**Test.** `U-proposed-change` — producer contract, the empty-list path, and the two refusals (unknown tool, invalid arguments) — plus an extension of `U-gate-percall` asserting the parked call's signature is byte-identical to the approved finding's `proposed_change`. That last assertion is the whole point of the workstream: without it, "the operator approves the object that fires" is a claim about intent. — met. `scripts/uat-v0.4.sh` (40 assertions, offline, wired into `dev/ci/presubmits/e2e.sh` after the v0.2 and v0.3 harnesses) runs `U-proposed-change` legs A–D over the real stdio MCP blocker from `testdata/uat` — the only offline source of a tool with a genuinely declared input schema, so the contract is checked against a real schema rather than the harness's idea of one — and `U-handoff` legs A/B for the edge. The byte-identity assertion is `U-handoff/A`: the parked question quotes `replicas=2`, *not* the `replicas=10` the same fake proposes when it picks a call for itself, and approving it fires `apply_change` exactly once with `replicas=2`. Unit coverage in `pkg/approval` (`changeset_test.go`, `producer_test.go`, `reportseam_test.go`), `internal/compose/writegate_test.go`, `pkg/graph/{graph,handoff}_test.go`, `pkg/agent/{schemafill,toolactor}_test.go` and `cmd/mast/toolschemas_test.go`. → **L7** *(green, with W7's legs still to come)*

> **Two things to expect from the offline fakes.** W1.4 finding (a) is the precedent: the fakes synthesize `finish_task` arguments from the declaration, so adding a nested `proposed_change` object to the schema will change what `pkg/agent/schemafill.go` produces, and the shipped bundle under `--model=echo` is the thing that breaks. Run `scripts/uat-v0.3.sh` early, not at the end. And a synthesized `proposed_change` naming a synthesized tool must not validate — if it does, `U-proposed-change`'s refusal legs are asserting against a fake that cannot fail.
>
> *Both landed as written.* The fakes default `proposed_change` to the **empty list** — a synthesized entry names a synthesized tool, which the producer contract correctly refuses, which would leave the fake retrying a report it cannot fix until the turn cap killed the run. A harness that wants a real one sets `MAST_FAKE_PROPOSED_CHANGE`. `TestChangeSetPropertyName` pins the field name across the `pkg/agent` ↔ `pkg/approval` import boundary, because a fake filling a field nothing reads looks exactly like a passing run.

> **Four findings from building it.**
>
> **(a) The announcement handing the approved calls to the executor must not be user-authored, and getting it wrong fails *silently*.** This cost the investigation, and it is the finding to carry forward. ADK authors an event `"user"` when its content role is user (`agent.getAuthorForEvent`), and its confirmation resume (`llminternal.RequestConfirmationRequestProcessor`, a default processor on every LlmAgent flow) scans backwards for the most recent user-authored event and **bails entirely if that event carries no FunctionResponse**. The graph's approval preamble, emitted with `genai.RoleUser` because that is how it reads, therefore landed between the operator's confirmation and the executor and disabled the resume: the run ended idle, nothing was applied, no error anywhere. The fix is one enum value — `genai.RoleModel` — and the executor still sees the text, because `ConvertForeignEvent` re-delivers a foreign-authored event as `"For context: [<author>] said: …"`. `TestApprovalAnnouncementIsNotUserAuthored` and `U-handoff/A`'s call count are what keep it fixed; recorded in [`./spike-findings.md`](./spike-findings.md).
>
> **(b) The validator lift needed a *name→schema resolver*, which is the part the plan did not see.** `normalizeEdit` split into `approval.InputSchema(tool.Tool)` and `approval.NormalizeArgs(name, schema, args)`, and W2.5's edit path now calls the same `NormalizeArgs` — one definition of "schema-valid arguments", as intended. But W7.0's caller holds a tool *name* and no instance, and the workload's `tool_catalog` carries names, not schemas: the schemas live on the live toolsets. `cmd/mast/toolschemas.go` is the missing piece — a cached, refreshing lookup over the daemon's toolsets, because an MCP server's tool list changes under a long-lived daemon. `pkg/workload/bundle.go` needed no change, as predicted.
>
> **(c) `arguments` is a JSON *string* on the wire, and that is forced rather than stylistic.** ADK validates a model's report against the declared output schema by walking nested objects and refusing any key the schema did not declare (`internal/utils.ValidateMapOnSchema`), and mast's own roster loader refuses an object property with no declared properties from the other direction (`pkg/specialists.checkSchema`) — for the good reason that it would accept anything. An arguments object is free-form by definition: its keys are whichever tool the finding names. So the wire form is a string, mast parses it, and mast checks it against the real tool's real schema — a stronger check than the report schema could ever have made. `ProposedChange.UnmarshalJSON` also accepts the object spelling, because that is what mast itself writes into durable records and grants.
>
> **(d) Two change executors in a roster turns the handoff off; it is not a load error.** The first cut refused to `Build`, and that broke a shipped-roster derivative already in the v0.3 acceptance pass — the shape is legal, mast just cannot tell which executor a finding meant. `graph.Build` now succeeds, `Config.Logger` gets a loud `Error` naming the roster and both executors, and the diagnoser→executor edge is simply not wired. A capability silently absent is the failure mode this is trading against, hence the log line rather than nothing.

### W7 — `per_change_set` *(gated on W7.0)*

✅ **Shipped 2026-08-15.** Approving one parked call with `scope: change_set` now mints a grant for **each remaining call in the set**, and the per-call gate spends it silently instead of asking again. `pkg/approval/grant.go` holds the record and the two bounds — a wall-clock `ExpiresAt` and a `Precondition` snapshot of the world the operator answered against; `pkg/approval/grantgate.go` holds the three verbs the gate calls (`checkGrant`, `spendGrant`, `voidGrant`) plus `planGrants`, which refuses a `change_set` verdict outright rather than narrowing it when anything about the set is un-grantable. A grant authorizes one exact normalized `(tool, arguments)` signature, is durable, is single-use, expires, and is re-read against the cluster before it fires. Policy still runs in front of it, and spending one records `DecisionAllowOnce` through the same `permissions.Gate` — the grant removes the *question*, never the accounting.

**What.** A grant-minting path **in front of** the W2 gate, not a second mechanism: mint N grants bound to exact normalized `(tool, arguments)` signatures, which the per-call gate consumes silently. Durable minted-not-chosen grants on the resume-token pattern, consumption paired against the outbox record, plus the freshness bound and precondition re-check the approval window demands, plus the legibility rule (narrow named tools only — an operator cannot approve what they cannot read).

**Where.** `pkg/approval/` (the gate is a runner plugin registered by `internal/compose.WriteGate` at every construction path — the grant store must be reachable from all four, per W2.4's lesson that an unexercised path is not a path); `pkg/effects` for the outbox pairing; the resume-token semantics in [`./durable-execution-design.md`](./durable-execution-design.md). W2.3 already refuses `AllowSessionVerb`/`AllowSessionTool`/`AllowAlways` on mutating tools and admits "change-set-minted exact-signature grants" as the one exception — W7 is what makes that clause real rather than reserved.

**Done when.** An operator approves N mutations once; a crash after call 3 of 5 resumes knowing which fired and re-fires none; a stale change set is refused back to the operator rather than silently applied. — **met 2026-08-15**, all three, though the middle one is met by two mechanisms rather than one: a grant records the `ConsumedBy` function call id, so a re-dispatch of the *same* call re-uses its grant and a second identical call finds it spent (`TestGrantIsSingleUse`, `TestGrantSurvivesARestart`); a call that was in flight when the process died is the recorded-effect outbox's subject, not the grant's, and it still refuses to replay (`scripts/uat-v0.2.sh` S1).

**Test.** `U-changeset-crash`, `U-changeset-stale`. → **L7** (with W7.0) — met, and widened. `scripts/uat-v0.4.sh` grew `U-changeset` legs A–E over a two-call set: **A** one answer runs both calls and asks exactly one question; **B** the control — `scope: once` on the same set still parks the second call, so A is not passing on a runtime that stopped parking; **C** the cluster moves while the first approved call is held open at the blocker and the second call's grant is voided (this is `U-changeset-stale`); **D** the window runs out with the cluster unchanged, so the wall clock is shown to work on its own and not as a second opinion on the read; **E** the daemon is SIGKILLed while the question is open and the approval arrives at a process that never saw the diagnoser (this is `U-changeset-crash`). 92 assertions, offline. Legs C and D assert on the *reason* the grant was voided, not merely that one was: both bounds void through the same path, and a leg that only counted the void would pass on the other clock. Unit coverage is `pkg/approval/grant_test.go`, plus `pkg/workload/precondition_test.go`, `internal/compose/writegate_test.go` and `cmd/mast/toolschemas_test.go` for the declaration, the startup refusals and the read. **New: `scripts/live-kind-v0.4.sh`** — see §2.

> **The freshness bound needs a definition, not just a duration.** "Stale" is cheap to implement as a wall-clock TTL and that is not what the risk is: a change set approved 20 seconds ago against a cluster that has since rolled is stale, and one approved an hour ago against an untouched deployment is not. Expect to need a precondition re-read (resourceVersion, generation, replica count — whatever the proposal's tool actually depends on) and to state which one in the design doc. A TTL alone should be treated as the fallback, and if it is what ships, say so in the release notes rather than letting "freshness bound" imply more.
>
> *Both shipped, and the doc says which is which.* The precondition is the check; the TTL is the backstop. A tool declares its own re-read in `tool_catalog` — `precondition: {read, args, args_from, fields}` — because mast cannot synthesize it: it does not know which tool reads the object a write is about, or which of the write's arguments names it. The bundle knows both. `hitl.change_set_ttl` sets the wall-clock window (default 10m, chosen to be far longer than an approve→execute round trip and far shorter than the hours over which an operator forgets what they approved). A tool that declares no precondition gets the TTL and nothing else, and the parked question **says so** rather than implying a check mast is not making.

> **Five findings from building it.**
>
> **(a) A precondition over the field the set rewrites is self-invalidating, and that is the design working.** The snapshot is taken once, at mint. So a two-call set over the *same* object — scale to 2, then to 3 — has call 1 move the field call 2 was checked against, and call 2 re-parks. The fix is not in mast: it is that a set's calls should each be checked against **their own** object, which is what `args_from` is for (`{name: deployment}` turns `scale_deployment(deployment=api, …)` into `get_deployment(name=api)`). This is why the live tier scales two Deployments rather than one, and it is the sentence to put in front of anyone declaring their first `precondition:`.
>
> **(b) `effects.NewPredicate` classifies an unlisted tool as mutating, which makes an undeclared precondition read a startup error.** A freshness check that changes the cluster is not a check, so `internal/compose.changeSetGrants` refuses to build a roster whose precondition read is mutating — and since an unlisted tool *is* mutating by default, the refusal fires on a read the catalog simply forgot to list. The error names `mutating: false` explicitly, because "your read tool is mutating" is baffling advice when you never said it was.
>
> **(c) ADK returns `{"output": <structured content>}` for an MCP tool that sends structured content, and the text otherwise** (`adk/v2@v2.2.0/tool/mcptoolset/tool.go`). A declared field path has to be right about that wrapper, so every `fields:` entry in this repo starts `output.`. The offline fixture found this the expensive way: `testdata/uat/blocker`'s `read_status` returned an empty struct, so every read digested identically and leg C passed both calls with no freshness check ever failing. A precondition over a tool that returns no structured content silently compares nothing to nothing.
>
> **(d) The outbox pairing the plan called for was nothing to build.** `pkg/effects` is a separate runner plugin: a granted call reaches the tool by the ordinary path, so its intent is recorded exactly as an operator-approved one is. The grant is *in front of* the gate, as the plan said, and staying there is why nothing downstream needed to learn about it.
>
> **(e) The offline fake needed fixing before the harness could measure the set, and the bug looked like a mast bug.** A resumed turn carries the approval preamble more than once — the branch keeps the original and the resume re-announces it — so `pkg/agent/toolactor.go`'s regex saw four entries for a two-call set and looped back to call one after finishing the set, parking a call nobody proposed. Legs A and E failed as "mast asked an extra question". Reading only from the *last* `ApprovedCallsMarker`, and pairing entries positionally against what the history shows already issued, is the fix; `TestToolActor_ApprovedSetRunsInOrder` pins it.

### W8 — Decision feedback loop *(falls out of W2.5; independent of W7)*

**What.** Log every approve / reject / edit verdict as a labelled eval example. *"Human edited 10 replicas → 4"* is the highest-signal data the system produces, and it arrives free now that the verdict is three-valued and the `AppliedEdit` record carries both argument sets and an authenticated approver.

**Where.** `pkg/approval/edit.go`'s `AppliedEdit` (proposed call, executed call, both argument sets, approver, note) is already the record; `pkg/transcript` already projects it. What is missing is the harvest: an exporter into the shape `internal/evals` loads, and a decision about where the rows land (a file under `testdata/evals/`, a `mast sessions export-decisions` subcommand, or both).

**Done when.** An approve, a reject and an edit performed against a live session each produce a labelled example that `internal/evals` can load and score, and the edit's example carries the *diff* — proposed arguments and executed arguments — not just the outcome.

**Test.** `E-feedback-capture`. → **19**

> **Do not harvest into the ported corpus.** `testdata/evals/scenarios/langchain-sre.jsonl` is a verbatim port with a provenance header and a count check (`TestLoadDataset_PortedCorpus`); mixing mast-generated rows into it destroys the one property that makes it a comparison baseline. Harvested decisions are a second dataset with their own header saying where each row came from.
>
> **This is the workstream with a privacy surface.** A verdict row carries an approver identity and whatever arguments the operator typed, which for a remediation tool is cluster topology. Decide before shipping whether the exporter redacts by default and what the opt-in looks like; do not discover the question when someone points it at a production session store.

### W4.1 — `scheduled:` on `EdgeTrigger` *(independent)*

**What.** A bundle fires on an interval, with jitter, and the schedule survives a daemon restart.

**Where.** `pkg/workload/bundle.go:121-126` already says *"other transports (message queue, scheduled) will join here."* The scheduler exists: `cmd/mast/pausesched.go` (`push` / `earliest` / `fireDue` / `seed`) already survives restart via the transcript store, which is why this is a wiring task and not a subsystem. Jitter is not decoration — N replicas of the same StatefulSet waking at the same second is a self-inflicted thundering herd against one API server.

**Done when.** A bundle fires on an interval and the schedule survives a daemon restart.

**Test.** `U-scheduled` — `scripts/uat-v0.4.sh`: a short interval fires twice, the daemon is `kill -9`'d between fires, and the restarted process fires on the original cadence rather than restarting the clock or double-firing the missed tick. Which of those two a missed tick should do is a decision this task makes and records; "catch up" and "skip" are both defensible and silently picking one is not. → **8**

> **A scheduled trigger is the first ingress with no caller.** Every existing entry point has an authenticated caller — that is where W2.1 gets the approver identity from. A timer does not. Whatever a scheduled run's audit rows say about who initiated it (`mast:scheduler`, by analogy with the existing `mast:internal`), it must not be a value that can be confused with a human, and a mutating call in a scheduled run still parks for a real approver.

### W1.1a — Provider-portable specialist tiers *(promoted into v0.4; blocks nothing, unblocks W4.3)*

✅ **Shipped 2026-08-15.** `tier: small | mid | frontier` ships beside `model:` as the portable spelling of the same override. A spec declares how much model the step is worth; `internal/compose/tier.go` derives the provider family — the explicit `--provider` alias when there is one, else the root model id's prefix, which is the dispatch `BuildModel` already makes — and resolves it through `pkg/taskclass.ModelForTier`, the same table `--task` uses. One roster line, `tier: small`, is `gemini-2.5-flash` under a Gemini root and `claude-haiku-4-5` under an Anthropic one.

Resolution goes *through* the memoized `ModelResolver` rather than beside it, so every property `model:` earned in W1.1 carries over unchanged: one client per resolved id, an unresolvable tier fails the build instead of inheriting the parent, and an offline-fake root collapses tiers back to itself — checked *before* the family is derived, since `echo` has no family and a tiered bundle must still run credential-free. `model:` and `tier:` on one spec is a load error, not a precedence rule.

**The half that was easy to ship broken:** `internal/compose.MeterScopes` priced off `s.Model`, so a tiered specialist would have run on the cheap model and been *billed at the parent's rate* — the bundle right, the run right, the number wrong. Both paths now go through one `SpecModelName(spec, provider, rootModelName)`, and `MeterScopes` takes the provider for it.

**Where it is exercised, not just declared.** `examples/workloads/ns-audit` is now tiered — four `tier: small` analysts, a `tier: mid` synthesis, which is the assignment its own `_synthesis.tmpl` comment used to say belonged in someone else's bundle. It loads and runs unmodified under `--model=echo` (collapse), under Gemini and under Anthropic; the startup log names the resolved id per specialist (`specialist tier resolved`), because what a tier became depends on how mast was started and cannot be read off the bundle. `scripts/uat-v0.3.sh` drives that bundle, so the collapse is covered end to end by an existing E-tier leg rather than by assertion.

**Test.** Unit: tier→id per provider family and the refusals (`internal/compose/tier_test.go`), the build honoring/refusing a tier (`pkg/specialists/register_test.go`), the load-time enum and the mutual exclusion (`pkg/specialists/loader_test.go`), and `TestMeterScopes_TierPricesAtItsResolvedModel` for the pricing half. E: `scripts/uat-v0.3.sh` unchanged and green over the now-tiered bundle. → no row of its own; it is what lets **10** be earned honestly rather than by hard-binding a shipped bundle to one vendor.

### W4.3 — Bounded analysis path *(independent; needs W1.3, shipped)*

✅ **Shipped 2026-08-16.** `dispatch: bounded` is a fourth shape: a roster of exactly one `SingleTurn` specialist that declares an `output_schema:`, built as a one-node workflow (`internal/compose/bounded.go`). No router turn in front of it and no tool loop under it, so one incident is one model call — and because the specialist is toolless, the contract is forced the genuine way: ADK puts the schema on the request itself (`Config.ResponseSchema` + `ResponseMIMEType: application/json`) and validates the reply before the turn may end, rather than hanging it off a `finish_task` declaration.

**The refusals are the feature.** Two specialists, a Task-mode spec, a spec with no `output_schema:`, or `planner.enabled` alongside — each is a build error naming what it found, before a tier is resolved or a provider client is opened. The reasoning is one sentence in four shapes: a second specialist needs something to choose between them, a Task specialist runs a tool loop to a `finish_task`, prose needs a reader, and a planner is an orchestrator — and the orchestrator is the thing this shape is defined by not having. A shape whose whole claim is a number has to refuse every roster it could not keep the number for.

**The question the plan said to resolve early, resolved.** A fourth shape, not a mode on `oneshot.go`. The one-shot path already wraps a non-Chat agent in a one-node workflow, which is most of the construction — but it has no bundle (so no `hitl:` policy, no `tool_catalog`), no roster (so no specialist file to carry `output_schema:` or `tier:`), and no meter scopes, which are derived from specs. It also cannot be scheduled: `--task` exits after one turn, and W4.1 fires *workloads*. A bounded cycle that a timer wakes is a workload, so it composes like one. `RosterShape` never infers `bounded` either, and that is deliberate: one SingleTurn specialist with a schema is what a workload looks like on day one, and inferring would silently replace a coordinator's own voice with the specialist's JSON report, with no error raised — the same reasoning as cmd/mast's terminal coordinator default.

**Finding — the offline fakes could not answer a forced schema at all.** `pkg/agent/schemafill.go` filled `finish_task` arguments and nothing else, so a toolless SingleTurn specialist with an `output_schema:` got `[echo] acknowledged: …` (or, from `toolactor`, a bare reason word) and the run died on ADK's output validation: `output validation failed: failed to parse output JSON`. The bounded path could not be exercised offline at all, and nothing said so, because no fixture had ever been that shape — the same class of gap W1.3 left behind and `U-report` closed. Both fakes now answer `Config.ResponseSchema` through the same filler the `finish_task` path uses, so a roster that changes its report shape changes both answers at once, and `MAST_FAKE_SCHEMA_VIOLATION` reaches the new path too (a SingleTurn violation is terminal by construction — there is no giving-up turn to pair with it).

**Where it is exercised, not just declared.** `examples/workloads/bounded-triage` — one `tier: small` SingleTurn specialist, the shipped `finding.json` byte for byte, no `tool_catalog` and no `hitl:` block, because a shape with no tools has no write surface to gate. `U-bounded-cost/steps` drives that shipped bundle, not a fixture.

**Test.** Unit: the shape builds and the four refusals name what they found (`internal/compose/bounded_test.go`), `RosterShape` still says coordinator for a bounded-shaped roster, the enum/flag/loader accept `bounded` and reject the near-miss `bound` (`pkg/workload/loader_test.go`, `cmd/mast/dispatch_test.go`), both fakes answer and can violate a forced response schema (`pkg/agent/schemafill_test.go`), and `mast.RunWorkload` over a bounded bundle reports `Usage.ModelCalls == 1` with a parseable report (`mast_test.go`). U: `U-bounded-cost/steps` in `scripts/uat-v0.4.sh` — one inject into the shipped bundle, `session_model_calls` **and** `mast_model_calls_total` both reading 1, the finding contract in the reply, no `finish_task` anywhere in the log, plus the refusal leg pointing `--dispatch=bounded` at the fourteen-specialist gke-triage roster and asserting the daemon does not come up. → **10**

> **`U-bounded-cost` is named by two rows and only one of them is in this release.** Row 9 (W4.2, zero-token collection) needs lookout's MCP mode and is v0.5. The script has two independently-runnable legs from the start — `U-bounded-cost/steps` (this task: one call, fixed step count) and `U-bounded-cost/collect` (v0.5: zero tokens on the collection leg, present and stubbed) — so row 10 goes green without row 9's leg existing, and nobody later reads a green `U-bounded-cost` as evidence for both.
>
> **This task is where the `tier:` decision came due — and it is settled.** "One *cheap-tier* call" means the bounded path names a small model, and W1.1 finding (b) was that `model:` takes a concrete id, so a shipped bundle declaring one hard-binds every forker to that provider. Of the three ways out — promote W1.1a, defer the "cheap" half, or accept the bind — **the first was taken on 2026-08-15 and W1.1a shipped ahead of this task**. The bounded path therefore declares `tier: small` and the "cheap" half of this task's claim is real on any provider. The two rejected options are recorded because the reasoning outlives them: deferring would have shipped a row-10 test that asserts step count while the word "cheap" in the capability went unmeasured, and accepting the bind would have made a shipped bundle a vendor choice for everyone who forks it.

### W0.6 — `J-cost-tier`, and turning the nightly on *(independent; part (b) needs repo admin)*

**What.** Two halves, both required for row 1.

**(a) The test.** ✅ **Shipped 2026-08-16.** `internal/evals/judge/cost.go` runs a two-specialist roster — a `tier: small` analyst under a `tier: frontier` synthesis, fan-out dispatch — against the nightly's live root, folds every streamed event into a `budget.Meter` built from `compose.MeterScopes`, and then reads the per-scope snapshot back and asks whether the analyst's dollars are its own.

W1.2 finding (b) is why this could not be an E-tier test, and the code says so where a reader will hit it: an offline-fake root collapses every `model:` and `tier:` back to itself, so under `echo` the two rates the check compares are the same rate and the row would pass by construction. `RunCost` refuses that configuration through a sentinel (`judge.ErrCostNeedsLiveModel`) the harness routes on — under `--model=echo` the board prints `J-cost-tier: SKIPPED … this is not evidence that tiered pricing works` and records no Problem, because what this configuration cannot answer is the question, not mast.

**Each row states the counterfactual.** A row is `analyst / small / claude-haiku-4-5 / 3 calls / 4200 tokens / billed $0.0042 / at root $0.3150 / $0.00100 per 1K`. "The analyst was not billed at the parent's rate" means nothing without the number it would have been, and the check exists precisely because that difference is the whole point of a tier.

**Three ways the check refuses to be vacuous**, each of which was a way to ship a green row that proves nothing:

- **Resolved is not the same claim as ran.** A tier that resolved to haiku and *ran* on opus would price correctly and cost wrongly. Each row carries the distinct `ev.ModelVersion` values the provider reported for that specialist, prefix-matched against the resolved id (providers append a build date), and a disagreement is a finding.
- **A roster whose tiers all collapse onto the root prices correctly and compares nothing.** Under the default Anthropic root, `tier: frontier` *is* the root — that row is labelled a control, not a measurement, and if *every* row is one the whole board is a finding.
- **Zero calls is a finding, not a pass.** So is a call that reported no tokens, and so is a tier that resolved to a model `pkg/pricing` has no rate for.

**Its verdict gates where the scores do not**, and that is not an exception to §2 but an instance of it: the arithmetic over the meter's own numbers does not depend on what the model said. A mispriced tier is a mast bug with a live reproduction, so `CostBoard.Findings` become harness Problems and fail the nightly job. Corpus scores stay report-only.

Where: `internal/evals/judge/cost.go` + `cost_test.go`, wired into `runJudge` ahead of the 31 corpus rows — it is two specialists and one turn against the same credentials the corpus is about to spend minutes on, and a machinery failure is worth finding before that, not after. The mechanism it exercises is `compose.MeterScopes` + `SpecModelName` + `budget.Meter.Observe`'s per-scope rate.

**What it still cannot check without credentials**, stated plainly: the wiring between `RunCost` and a real provider. The roster's shape and every verdict are unit-tested (the specs price two genuinely different rates, resolve through the tier resolver, and reach no MCP server; `judgeCost` is pure arithmetic over hand-written boards), but that the live path accrues what it claims is exactly the thing only (b) can demonstrate.

**(b) The scheduler.** `.github/workflows/evals-nightly.yml` exists and **skips loudly** because three repo settings are unset: `vars.MAST_EVALS_VERTEX_PROJECT`, `secrets.MAST_EVALS_WIF_PROVIDER`, `secrets.MAST_EVALS_SERVICE_ACCOUNT`. Until they are set, no J-tier row can be green under the scoring rule, because nothing runs in CI. This half needs repo-admin access and is Gari's to do, not an agent's.

**Done when.** The scheduled nightly has posted a board unattended, that board carries a `J-cost-tier` result, and the tiered roster's analyst is priced at its own rate. **(a) is done; the row stays red until (b) makes the board appear.**

**Test.** self. Non-gating on the scores, per §2 — but `J-cost-tier`'s own findings *do* fail the nightly job, for the reason above. → **1**

> **Row 1 is the one row on the board that is red for want of a measurement rather than a mechanism.** Both halves of the capability shipped in v0.3 (W1.1 honors `spec.Model`; W1.2 prices an override at its own rate, with `TestMeterScopes_OverridePricesAtItsOwnTier` pinning it). The scoring rule is deliberately unforgiving about that distinction and should stay so — but it is worth saying in the release notes which kind of red each row is, because "we did not build it" and "we cannot run the test in CI yet" are different facts about the product.

**v0.4 = M4a + M5, plus the promoted W1.1a.** Seven tasks, one repo. The release claim is *"an operator approves the exact call that will fire, the loop runs on a schedule without an orchestrator, and every verdict becomes a labelled eval row."*

**Carried unchanged from v0.3 §5:** W2's record-shape decisions stand — approvals already carry an authenticated approver, so v0.5's Slack approvals arrive to find identity in the log rather than needing a migration.
