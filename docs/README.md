# mast: design docs

Design documentation for `mast` — the agent-infrastructure substrate for unattended, library-embedded, multi-provider, durable workloads. These docs describe the project as it's *currently designed*; the code lives in this repo (Phase 1 executed 2026-07-26, and the adapter ports from [`core-agent`](https://github.com/go-steer/core-agent) landed 2026-07-29 at the pinned SHAs [`./fork-design.md`](./fork-design.md) records). Ongoing sync with core-agent runs through [`./sibling-sync.md`](./sibling-sync.md).

## Reading order for someone landing cold

1. **[`./positioning.md`](./positioning.md)** — the thesis. What `mast` is, what it isn't, what gets kept / cut / reshaped from core-agent's surface. Strategy, not implementation.
2. **[`./fork-design.md`](./fork-design.md)** — the mechanics. How the fork actually happens: phasing, trigger conditions, sync discipline under (E)-sibling-products motivation, resolved decisions.
3. **[mast-web's `web-design.md`](https://github.com/go-steer/mast-web/blob/main/docs/web-design.md)** — the operator-facing UI. Why web (not terminal TUI); what we reuse from an earlier internal browser-WASM UI experiment and what we don't; stack decisions; deployment options.
4. **[`./specialists-design.md`](./specialists-design.md)** — the subagent-as-tool subsystem for mast-authored subagents. Schema, loader shape, composition with existing patterns. Coexists with skills as complementary authoring model (see #16).
5. **[`./workflow-scaffolding-design.md`](./workflow-scaffolding-design.md)** — the reference-graph library on ADK v2 primitives. Seven canonical shapes (fan-out-fan-in, sequential pipeline, supervisor+workers, autonomous loop, adversarial verifier, map-reduce, LLM-as-router) with domain wiring for mast's audience.
6. **[`./orchestration-design.md`](./orchestration-design.md)** — the unattended orchestration story: workload bundles (declarative operational profiles under `.agents/workloads/*.yaml`), the planner (supervisor-body agent with reference-graph vocabulary), bundle learning (audit-derived refinement), and evaluation + regression harness. One doc, four subsystems, one story arc.
7. **[`./durable-execution-design.md`](./durable-execution-design.md)** — the fourth pillar (unattended + library + multi-provider + durable). Pause/resume beyond HITL: programmatic pause, timed pause, external-signal pause, snapshot+replay, cross-runtime Python-ADK compat constraints.
8. **[`./observability-design.md`](./observability-design.md)** — telemetry as first-class operational surface (traces via OTel, metrics via Prometheus, structured logs, distributed tracing across MCP hops, alert integration back into the agent loop).
9. **[`./library-api-design.md`](./library-api-design.md)** — the public Go import surface for library-embedded consumers; extension points (custom providers, session stores, permission checkers, tools, specialist sources, workload sources, attach transports, observability sinks).
10. **[`./deployment-design.md`](./deployment-design.md)** — production topologies (Cloud Run, GKE, library-embedded, standalone); multi-instance coordination; multi-tenant tenancy; packaging.
11. **[`./memory-design.md`](./memory-design.md)** — mast-consumer view of the shared-memory / audit-derived-memory substrate; keyspace, reducers, state-bound reads, tenancy enforcement.
12. **[`./mcp-catalog-design.md`](./mcp-catalog-design.md)** — position doc + curated wiring templates for the MCP servers mast validates against (gke, prometheus, github, cloud-logging, slack + v0.2 expansion).
13. **[`./config-layout-design.md`](./config-layout-design.md)** — ties together `.agents/` file layout across specialists, workloads, MCP; discovery order; precedence rules; env-var overrides; hot-reload semantics.
14. **[`./a2a-design.md`](./a2a-design.md)** — Agent-to-Agent protocol integration: mast as A2A server (expose workloads as A2A skills) and client (call external A2A agents). Framework integration with Google Agent Registry / Runtime, kagent.
15. **[`./federation-design.md`](./federation-design.md)** — federation as pattern: one mast instance orchestrating N remote agents via multiple protocols (A2A, mast-native, HTTP/RPC). Planner's `invoke_remote_agent` vocabulary; topology archetypes (star / mesh / hierarchical); mast-to-mast handoff with cross-instance session state, HITL, durability.
16. **[`./skills-design.md`](./skills-design.md)** — SKILL.md format support (reinstated 2026-07-01 after GKE + Google teams began publishing skills as first-class artifacts). Coexists with specialists as complementary authoring model — specialists for mast-authored subagents; skills for consumed published templates. Publisher/consumer split, Google Agent Registry integration, policy layering (allowlist intersection, budget caps).
17. **[`./ag-ui-design.md`](./ag-ui-design.md)** — AG-UI protocol integration (agent↔user); the fourth of the four interop surfaces alongside MCP (tools), A2A (agents), and skills (task templates). Mast as AG-UI server for CopilotKit React apps + chat-platform bots (Slack et al. via `@copilotkit/channels-*`); mast as AG-UI client via federation. Interrupt lifecycle (a draft AG-UI extension — labeled bet) maps onto mast's durable pause/resume. All AG-UI ships v0.2 per the 2026-07-25 re-cut.
18. **[`./adk-v2-usage.md`](./adk-v2-usage.md)** — consolidated inventory of the ADK v2 constructs mast leans on (runner + agent modes, unified `agent.Context`, graph engine + node types, `agenttool`, HITL primitives, session events, unified span tree). Cross-references the companion docs where each surface area is decided; reference doc, not a strategy doc. Read before starting Phase 1 bucket 1.
19. **[`./model-support-design.md`](./model-support-design.md)** — combo requirements + design for model support beyond Gemini and Claude: managed providers (OpenAI, Vertex AI MaaS partner models, xAI, Bedrock, Azure) and self-hosted servers (vLLM, SGLang, Ollama, NIM). Names the eight-point bar a provider must clear to be called *supported* (R1–R8, cost and usage parity included), inventories the nine seams that assume **model-id prefix ⇒ vendor**, and proposes replacing that inference with declared **provider profiles** (dialect + endpoint + auth + tiers + capabilities). Three wire dialects rather than N adapters — `openai-chat` is the leverage, reaching Vertex MaaS *and* every self-hosted server *and* the managed long tail with one adapter. Carries the prioritized P0/P1/P2 lists and a six-slice sequencing where the mast-internal fixes (usage sidecar, profiles, backend-keyed pricing — closing [#178](https://github.com/go-steer/mast/issues/178)) land before the first new provider. §10 surveys [`charmbracelet/fantasy`](https://github.com/charmbracelet/fantasy) — which implements both OpenAI dialects and most of §5's provider list under Apache 2.0 — and proposes taking it as prior art and a conformance-test pattern rather than as a dependency, since its own `LanguageModel` seam would sit between ADK's `model.LLM` and the SDK and flattens the reported-vs-zero distinction R3 turns on. **A proposal: nothing in it is settled**, and it targets v0.5+. Docs-site mirror lands with the implementation, not the proposal.
20. **[`./triage-demo-plan.md`](./triage-demo-plan.md)** — v0.1 anchor use case: mast-native reshape of core-agent's GKE triage recipe. Workload bundle + thirteen specialists (eleven per-failure-mode + `SingleTurn` classifier + `change-safety-gate` HITL) + LLM-as-router workflow graph, tying substrate and subsystems together end-to-end against a real platform-team problem. Sanctioned pre-trigger prototyping scope per [`./fork-design.md`](./fork-design.md).
21. **[`./uat-v0.2-plan.md`](./uat-v0.2-plan.md)** — v0.2 end-to-end UAT plan: deterministic, credential-free, CI-runnable acceptance suite driving the whole durable-execution spine (outbox #70, pause/abort #42, boot auto-resume #41, observability #50) through a real daemon — nine cross-cutting scenarios with state/metric/exit-code assertions, harness shape (extends `scripts/demo-spike2.sh`), and a living A2A/AG-UI growth checklist. A dev/testing plan (like `triage-demo-plan.md`); no docs-site mirror.
22. **[`./v0.3-plan.md`](./v0.3-plan.md)** — the executable v0.3 work breakdown: SRE-agent parity across mast / `k8s-lookout` / `switchboard`. PR-sized tasks (`W0`–`W8`) with file anchors, definitions of done, and the named test that proves each; a **parity scoreboard** (19 rows behind + 6 lead rows to defend) that is the release-readiness view; and a four-tier test strategy (smoke / UAT / deterministic eval / live judge). Executes [`./assessments/langchain-sre-agent.md`](./assessments/langchain-sre-agent.md) §4, with one deliberate inversion — the eval harness lands **first**, as a red scoreboard, so progress is measured against a fixed baseline. A dev/testing plan; no docs-site mirror. **Still the canonical scoreboard and the record of what shipped**, including for later releases.
23. **[`./v0.4-plan.md`](./v0.4-plan.md)** — the v0.4 work breakdown: the six remaining **mast-only** tasks, with file anchors and exit criteria. Re-cuts the milestones the v0.3 plan left for v0.4 — v0.4 = M4a + M5 (W7.0 the typed change-set producer, W7 `per_change_set`, W8 decision→eval feedback, W4.1 scheduled triggers, W4.3 the bounded path, W0.6 the J-tier cost test), v0.5 = M4b (the lookout and switchboard halves) — so the release does not depend on two other repos' schedules. Adds no test tier and no second scoreboard; rows are still flipped in `v0.3-plan.md` §1. A dev/testing plan; no docs-site mirror.

24. **[`./v0.5-plan.md`](./v0.5-plan.md)** — the v0.5 work breakdown: **M4b, the parity claim**. Opens by recording that the dependency the v0.4 re-cut was waiting on has landed — lookout shipped `k8s_findings_diff` / `k8s_findings_ack` and the normalized subject key ([k8s-lookout#212](https://github.com/go-steer/k8s-lookout/issues/212)), switchboard shipped agent-initiated egress ([switchboard#22](https://github.com/go-steer/switchboard/pull/22)) — which flips two board rows nobody here had noticed, and unblocks W4.2/W4.4/W4.5/W4.6. Its §2 settles the one decision the four tasks share: **the collection and state-advance legs are mast's, not the model's**, because `findings diff` genuinely writes and a monitor that needs an approval to learn whether anything changed is not unattended. A dev/testing plan; no docs-site mirror.

25. **[`./v0.6-plan.md`](./v0.6-plan.md)** — the v0.6 work breakdown, and the first release plan the parity scoreboard did not choose. With the board at 17 of 19 at the time (18 of 19 since 2026-09-14, and the one open row turned out to be mast's — see [`./v0.3-plan.md`](./v0.3-plan.md) §1 row 16) and both open rows believed to be switchboard's, §0 records that the spine three releases ran on is spent and v0.6 has to state its own claim: **enforcement reaches every call the workload makes, and a ceiling stops a call before it is paid for.** Its §2 is the load-bearing part — a seam inventory that corrects the roadmap's easily-misread "both need a seam in front of the model call," showing the write gate/outbox (runner plugins, do not cross a dispatch) and spend metering (event-stream folding, crosses via `SubRunSink`) are different mechanisms in different layers, so v0.6 is two workstreams under one claim rather than one piece of work — while naming the transfer that *is* real, since `SubRunSink` proves a host-owned concern can cross the dispatch boundary without being a plugin, which is a fourth option [#235](https://github.com/go-steer/mast/issues/235) never listed. Opens `W9` (the gate reaches a dispatched call) and `W10` (a pre-call ceiling). A dev/testing plan; no docs-site mirror.

26. **[`./sibling-sync.md`](./sibling-sync.md)** — the sync-state ledger [`./fork-design.md`](./fork-design.md) § "Sync discipline under (E)" specifies: which core-agent SHAs are absorbed, which are n/a to the lean scope, which are still owed, and the security-fix correlation table. The *inventory* is generated weekly by [`../dev/upstream-drift`](../dev/upstream-drift) into a tracking issue; this doc holds the *verdicts*, because a commit count is not a decision. Start here before porting anything from core-agent. An operational ledger, not a design doc; no docs-site mirror.

27. **[`./outcome-evals-design.md`](./outcome-evals-design.md)** — the **O — outcome** tier: a real model against a real cluster, gating on an admitted roster. Settles the schema an external specification proposed ([#294](https://github.com/go-steer/mast/issues/294)) before any Go is written — what mast adopts (fixture-role indirection, probes-before-run, `changed_count_eq` as the blast-radius ceiling mast has never had), and five corrections where the spec assumes runtime mast does not have: `request_approval` is not and must not be a tool, `reverts_to_captured_state` needs a product feature ([#296](https://github.com/go-steer/mast/issues/296)) rather than a verifier, `intent_satisfied` structurally cannot express "two distinct objects were read", and the spec's Vacuity section attributes an upstream LangChain defect to mast and reverses its direction. Its §4 is the load-bearing part and was found by measurement: `intents.yaml` carries no rows for the hosted GKE MCP surface, so on GKE every `intent_satisfied` check in the corpus is vacuous — which settles the substrate on the merits rather than on cost, kind + `k8s-lookout`'s read-only MCP server, extending tier C's isolation discipline. §5.1 is the schema as it is actually enforced — `internal/evals/outcome` refuses a corpus that cannot measure what it claims to, and building it turned up two more corrections the spec's own rules contradict. §5.2 is the fixture provisioner: what it plants, what it refuses about a manifest, and why a role with no stated readiness condition fails construction. §5.3 is the grading half — the four verifiers, the three kinds of vacuity only a run can reveal, and the four rungs on which a board reds. §5.4 is the half that spends money: the tool surface is the intent table's own keys rather than a list, so every tool the model can call is one the grader can read; the server config is built in Go and the child gets no `HOME`, because clientcmd would otherwise fall back to the operator's real cluster; the 20-minute budget is a deadline rather than a job timeout, because a deadline reports which cases ran and a timeout reports "cancelled". **OQ2 is resolved there: the gate runs per-PR**, made affordable by `cancel-in-progress` rather than by a merge queue, and its unconfigured case fails rather than skips — the opposite of the judge nightly, because green-because-it-could-not-run is the inert rung §7 is written against. §5.5 is the replacement for the refused `request_approval` tool: what an `approval_requested` check reads off the durable log, and **OQ3 resolved there — it reads the gate's question and never the verdict**, since in an eval the harness supplies the answer. A dev/testing plan; no docs-site mirror.

28. **[`./compatibility-policy.md`](./compatibility-policy.md)** — how a covered thing is allowed to change, in force from v1.0 ([#304](https://github.com/go-steer/mast/issues/304)). The companion to [`../DESIGN.md`](../DESIGN.md) § "The v1.0 stability promise", which says *what* is covered: this says what counts as breaking (enumerated, including the two categories no signature change reveals — a default that alters behaviour, and validation getting stricter on a file that used to load), how long a deprecation is visible before the major that removes it (**two released minors and 90 days**, both), how a deprecation is announced on four channels, how long a release is supported (the current one; mast does not backport, and that is a description of eight releases before it is a policy), and why there is no experimental tier and will not be one. Supersedes the one sentence [`./library-api-design.md`](./library-api-design.md) has carried since 2026-07-01 and resolves its OQ 6. The one rule a test can hold is held by one: `deprecation_test.go` at the module root refuses a `// Deprecated:` marker that does not name the release removing it.

29. **[`./threat-model.md`](./threat-model.md)** — the security document this corpus did not have, for the review a platform team runs before deploying something that acts unattended ([#305](https://github.com/go-steer/mast/issues/305)). Largely collection: the trust boundaries, the four adversaries, the controls mapped to each, blast radius, and the known-accepted risks were all reasoned out in isolation across eight releases and were discoverable only by reading a YAML comment, five composition-time checks and half a dozen issues. Four things changed when the claims were checked against the code rather than carried over from the issue, and they are the load-bearing parts: **the workload bundle is a control-plane input that can reclassify a mutating built-in as read-only** (measured — engine control-flow calls are the floor and are not reclassifiable), so write access to the mounted ConfigMap is write access to what the workload can reach; **the inject listener does not refuse an unauthenticated non-loopback bind** while attach, A2A and AG-UI all do, and it is the surface that releases parked calls ([#361](https://github.com/go-steer/mast/issues/361)); **classifier-first's four "mandatory" constraints are unimplemented because the path is unshipped**, which is [#300](https://github.com/go-steer/mast/issues/300)'s failure shape and is now annotated in [`./orchestration-design.md`](./orchestration-design.md) rather than left; and the issue's own list of fragments was stale on [#290](https://github.com/go-steer/mast/issues/290), which closed measured 41/41 on live GKE. States plainly that mast does not defend against prompt injection and that the write gate is the defence — which makes the gate's coverage boundary a security boundary, and is why the planner-dispatch hole is a startup refusal rather than a tolerated caveat.

Each doc has a Resolved-decisions section at the bottom listing what's been settled in conversation; the rest is open for discussion.

## Assessments

[`./assessments/`](./assessments/) holds comparative and evaluative write-ups — findings against an external system, a competitive read, a retrospective. They are *inputs* to the design corpus, not part of it: an assessment records evidence and proposes work, but nothing it proposes is settled until the owning design doc says so and the cross-reference table below records it. Like [`./uat-v0.2-plan.md`](./uat-v0.2-plan.md), they carry no docs-site mirror.

- **[`./assessments/langchain-sre-agent.md`](./assessments/langchain-sre-agent.md)** (2026-08-12) — LangChain's autonomous Kubernetes SRE agent vs. mast v0.2.0. Their subagents map ~1:1 onto specialists and mast leads on durability, cost metering, multi-provider, and read-path depth (`k8s-lookout`); the gaps are the designed-but-unwired parts — structural read/write split + per-mutating-tool gate (`hitl_policy.on_mutation`), fan-out, cross-run finding state, chat egress + Slack interactivity, typed report contract, per-specialist model tier, eval harness. Includes a six-slice MVP plan across mast / switchboard / k8s-lookout.

| **A signature nobody can attribute is a signature over nothing** (2026-09-19, first slice of [#342](https://github.com/go-steer/mast/issues/342)).
