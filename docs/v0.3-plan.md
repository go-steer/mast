# mast v0.3 plan — SRE-agent parity, executable

**Date:** 2026-08-12 · **Status:** plan, not a design decision · **Target:** the functional equivalent of [`langchain-ai/sre-agent`](https://github.com/langchain-ai/sre-agent), spanning `mast`, [`k8s-lookout`](https://github.com/go-steer/k8s-lookout), and [`switchboard`](https://github.com/go-steer/switchboard)

This is the executable form of the six-slice plan in [`./assessments/langchain-sre-agent.md`](./assessments/langchain-sre-agent.md) §4. That doc argues *what* the gaps are; this one is the work breakdown — PR-sized tasks with file anchors, a definition of done, and the test that proves each one. Task IDs (`W1.2`) are stable and file directly as issues.

Like the assessment and [`./uat-v0.2-plan.md`](./uat-v0.2-plan.md), this is a planning artifact: decisions it surfaces belong in the owning design doc and [`./README.md`](./README.md)'s resolved-decisions table. No docs-site mirror.

## 0. One deliberate change from the assessment's sequencing

The assessment put evals last (P5, "gates everything after"). **Invert it.** The eval harness lands *first*, in W0, as a scoreboard that starts almost entirely red.

The reason is not process aesthetics. "How do we compare to LangChain?" is not answerable by reading diffs — it needs a measurement that exists before the work does, so each workstream can be scored against a fixed baseline rather than against a target that moves as we learn what we built. Building the measuring stick last means the first honest comparison happens after the last PR, which is the wrong time to discover a gap.

Cost objection doesn't hold: three of the four test tiers are free (§2), and the metered tier is roughly **$5–15 per nightly run** across 31 scenarios. That is not a number worth sequencing around.

## 2. Test strategy — four tiers

The assessment's §5 proposed two tiers and **claimed the deterministic tier could gate `tool_coverage`**. That is wrong, and correcting it is load-bearing for this plan.

`tool_coverage` measures *which tools the model chose*. A scripted provider or `toolactor` does not choose — its trajectory is the fixture. Replaying a scripted trajectory and asserting the tools match the script asserts that the script equals itself. **Measuring agent quality, and therefore comparing to LangChain at all, requires a live model.** What the free tiers gate is *mast's guarantees*, which is a different and equally necessary thing.

| Tier | What it proves | Provider | Cost | Cadence | Harness |
|---|---|---|---|---|---|
| **S — smoke** | it builds and runs offline | echo | zero | every PR | `go test` + per-starter `main.go` run (the `scripts/demo-spike2.sh` bar) |
| **U — UAT** | the *system* behaves: routing, gating, metering, crash/resume, HTTP contract | `scripted` / `toolactor` | zero | every PR | `scripts/uat-v0.2.sh` **+** `scripts/uat-v0.3.sh` → `dev/ci/presubmits/e2e.sh` *(both, in order — the v0.3 script adds to the v0.2 spine, it does not replace it; W1.4 finding (d))* |
| **E — deterministic eval** | mast's *differentiators* hold under adversarial trajectories: exactly-once, refusal, rejection, budget, edit-application | `scripted` / `toolactor` | zero | every PR | `scripts/evals.sh` → `dev/ci/presubmits/evals.sh` |
| **J — judge / live** | *agent quality*, and the only LangChain-comparable numbers | real provider | ~$5–15/run | nightly + pre-release | same harness, `--tier=judge` |

Tiers S/U/E are gates: red blocks the PR. Tier J is a **report**, not a gate — a judge score is too noisy to block on, and gating on it invites tuning the judge. It posts a scoreboard delta.

**Golden-trace replay** sits between E and J: capture one real trajectory per scenario (metered, manual, `mast sessions capture-golden` per [`./orchestration-design.md`](./orchestration-design.md)), commit it, replay free forever after. It catches *harness* regressions against a frozen model decision — not model regressions. Worth doing for the ~8 scenarios in the anchor workload; not worth doing for all 31 until the trajectories stop churning.

**Naming.** Tests referenced in the scoreboard use their tier prefix: `U-gate-crash`, `E-approval-edited`, `J-severity-accuracy`.

**Conventions inherited from the v0.2 UAT** (non-negotiable, see [`./uat-v0.2-plan.md`](./uat-v0.2-plan.md) "Harness shape"): deterministic, credential-free, offline; real SQLite `--session-db` for anything crossing a restart; state under `${TMPDIR:-/tmp}/...` (house rule #5); `set -euo pipefail` + `trap cleanup EXIT`; bounded `wait_for` polls, never bare sleeps; every new script wired into `dev/ci/presubmits/all.sh` *and* `.github/workflows/ci.yml` so local == CI (house rule #6).

1. **Coverage is not the problem.** Of the 23 distinct tools their dataset expects, **22 map to a lookout read intent** and several map to something strictly better: `kubectl_get_pod_logs` → `k8s_triage_logs` (150k→350 tok distillation), `get_cluster_summary` → `k8s_cluster_health` (ten-category scorecard). 2. **Their own expectations are partly unreachable.** Seven of the authoritative dataset's 23 tool names — `kubectl_describe_service`, `kubectl_describe_node`, `kubectl_describe_ingress`, `kubectl_describe_hpa`, `kubectl_get_service`, `kubectl_get_secrets`, `kubectl_get_pvcs` — **do not exist in their own registry** — checked against the full 63-name pool in `tools/__init__.py` (`READ_TOOLS` + `WRITE_TOOLS`, helm included), not just the `kubectl_*` subset (the registry has `kubectl_get_services` and `kubectl_get_pvc`; the dataset asks for the singular and the plural respectively). That is 16 of 71 tool references, ~23%, that no run can satisfy. Their published `tool_coverage` therefore has a hard ceiling well below 1.0, and is not a baseline we can adopt without normalizing for it.

3. **Set overlap punishes consolidation** — the load-bearing one. Therefore the checked-in artifact is `testdata/evals/intents.yaml`: each of their tool names → an **intent id**, and each lookout tool → the set of intents it satisfies. A scenario satisfies an intent when *any* trace call claiming it appears. Phantom tools from finding 2 get an intent and are marked `unreachable_upstream: true` so the ceiling adjustment is explicit rather than folded into a score.

> **Three decisions this workstream had to make that the plan did not name.** Recording them here because W0.4's allowlist and W0.5's reporting both depend on them.
>
> - **A vacuous 1.0 is marked, not hidden.** Upstream's `tool_coverage` is 1.0 on all 31 rows because there is nothing to measure, and nothing in its output distinguishes that from a perfect run. Every `Result` therefore carries `Vacuous`, set when the score is 1.0 for want of anything to score — no expected tools, no expected severity, no mutating effects. W0.4 should treat a wholly-vacuous corpus as a harness failure, not a green board.
> - **The severity extractor is deliberately not upstream's, in both directions.** Upstream's bracketed `\[(CRITICAL|WARNING|INFO|OK)\]` matches 0 of 31 expected responses. mast's reads the expected side the way the corpus is actually written (bare leading token) and accepts on the actual side the forms a model plausibly emits for the same claim — `CRITICAL:`, `[CRITICAL]`, `**CRITICAL**`, `## CRITICAL`, `Severity: CRITICAL`. > - **`exactly_once` keys on tool name plus canonicalized arguments, not call ID.** Scaling two different deployments is two effects; scaling one deployment twice is the violation. Keying on the ID would make the metric structurally incapable of failing, which is the exact failure mode found in upstream's harness.

> **Divergence from `pkg/effects`, on purpose.** `pairScan` *defers* long-running calls, because at turn start the runtime has not yet decided whether they ran. An evaluator scores a finished run, where a long-running call that completed is an effect like any other — deferring it would blind `exactly_once` to a re-fired blocking tool, which is the failure it exists to catch. This is the one place the two walks differ, and `TestTraceFromEvents_Exclusions/long-running-calls-are-kept` pins it.

> **(b) A write Role in `deploy/base` is a write Role in the wrong namespace.** The base pins `namespace: mast-triage` on everything it renders, so a Role carried there lands in the daemon's *own* namespace — the one namespace where the grant is useless — and an operator retargeting it would widen the base for every deployment built from it. Hence `deploy/remediation-target/` as a separate kustomization with its own `namespace:`, and a lint test asserting the base's `resources:` cannot reach it. The RoleBinding's subject then crosses namespaces (SA in `mast-triage`, Role in the target), which is the shape that makes "which namespaces may mast change" a list of applies rather than a field.
>
> Both manifests were validated against a live GKE 1.36 API server with `kubectl apply --dry-run=server` (nothing applied, nothing persisted), and `rbac-matrix.sh` was smoke-run against that cluster: its 9 expected-**no** cells pass there today, and its expected-**yes** cells correctly report the grant's absence on a cluster where nobody applied it.

*Exit for W2:* a diagnosis specialist structurally cannot mutate; a remediation call parks *before* firing, survives `kill -9`, and resumes with the operator's edits applied. **UAT green here is the gate on W7 starting.** — **met 2026-08-14**, and with it M3, which is the last milestone in v0.3's M1–M3 scope. The one thing the exit does *not* cover, because it was never phrased in terms of the cluster: W2.6 finding (a). The gate is what mast enforces; what the cluster will accept from mast is one IAM binding away from being much wider.

> **W2 finding (c) — the gate is reachable, but nothing in the shipped bundle reaches it.** Found 2026-08-14 on the first live run of the anchor workload against a real GKE cluster (`std-simian-test`, a real `ImagePullBackOff` on `online-boutique/emailservice`). Every clause of the exit above is true of the *mechanism* and is proven by `U-gate-*`, which drives a mutating call with `--model=toolactor`. What no test covers is how a mutating call comes to exist in the first place, and the answer today is: it doesn't. **`change-executor` is an orphan node in both shipped dispatch shapes.** In `graph`, the topology is `Start → classify → route_by_reason → run_<specialist>` and every specialist node is *terminal* — there is no edge from a diagnoser to the executor, and the route key is the classifier LLM's own reply, so the only way in is for a classifier asked to name a *failure mode* to answer `change-executor` (it doesn't; injecting `reason: change-executor` routed to `_fallback`). In `coordinator`, `pkg/router.defaultCoordinatorInstruction` — written before W2.4 created the executor — says "summarise the specialist's finding… Do not attempt remediations yourself," and the live run did exactly that. So M3's demonstrable claim holds for the gate and **not** for the loop that would exercise it: gated remediation is real, unattended remediation is not reachable, and the honest phrasing of the demo is "a remediation call cannot fire without an operator", not "mast remediates, gated".
>
> Wiring the hop with a coordinator prompt is the wrong fix and W2.4 already says why: the read/write boundary used to be prompt text (*"Do NOT mutate anything on your own initiative"*), and replacing that with a structural check is the whole point of the workstream. A prompt-wired forward path is the same mechanism mirrored. It also would not work — there is nothing typed to hand over. `finding.json`'s `recommended_actions` is `array<string>`, and the live run's was `"Suggest 'kubectl rollout undo deployment/emailservice -n online-boutique'"`: prose, addressed to a human, naming a CLI verb that is not a tool the GKE MCP server offers. The executor would have to re-read the cluster and re-derive the change, so the finding an operator approved and the call that fires would be two artifacts with no link between them. **The missing piece is a producer, and it is scoped as W7.0 below.**

> **W3 findings — the plan was written from reading, and the substrate reads differently than it behaves.** Seven, in descending order of consequence.
>
> **(a) A `workflow.ParallelWorker` branch cannot use a tool at all.** W3.1 as written specified `NewParallelWorker`'s `maxConcurrency` argument, so this is the plan being wrong about the primitive rather than about a detail of it. ParallelWorker's `runWrappedOnce` keeps only `extractOutput` hits and yields nothing else upward — its own doc says so, and reading it as "branch chatter is suppressed" is how it got into the plan. What that actually means: **an LLM agent's working memory is the session event list.** `internal/llminternal/contents_processor.go` rebuilds `req.Contents` from `ctx.Session().Events().All()` on every model call, and the only thing that appends to a session is the *runner*, processing events yielded up to it. Suppress the yield and model call #2 gets a prompt byte-identical to call #1 — the analyst cannot see its own tool result, calls the same tool again, and loops until something cancels it. Measured directly: the same analyst behind the same `NewAgentNode`/`RunNode` machinery saw `text text text call:look resp:look{seen:a pod}` on call #2 through a sequential graph node and `text` through a ParallelWorker branch. This is not a corner case; it is every analyst that reads a cluster. The fan-out is therefore built on `agent/workflowagents/parallelagent`, which funnels each sub-agent's events up and blocks the sub-agent until the parent has appended them. Branch isolation survives the change — it comes from branch *tagging* (`eventBelongsToBranch` admits only an event on the invocation's own branch prefix), not from suppression, so analysts still cannot read each other. `TestFanoutSubstrate` runs one branch body under both primitives and asserts the opposite outcomes.
>
> **(b) A Task specialist cannot be a `parallelagent` sub-agent, and `parallelagent` has no concurrency cap.** Two composition facts that cost the shape a wrapper apiece. `parallelagent` calls `agent.Run`, and Task-mode completion is implemented on the `AgentNode`/`RunNode` path — a Task specialist run the other way returns from `finish_task` and keeps going. So every branch is its own single-node workflowagent whose `DynamicNode` calls `workflow.RunNode` (legal only because `DynamicNode.Run` installs its own sub-scheduler unconditionally). And since `parallelagent` starts every sub-agent at once, `max_concurrency` is mast's to enforce: a per-invocation semaphore each branch acquires before its model call, forgotten when the activation ends so a long-lived daemon does not accumulate channels.
>
> **(c) Per-specialist budgets did not bite inside a ParallelWorker branch — and the seam the plan named would have metered nothing.** W1.2's scopes bucket by `session.Event.Author` over the runner's stream, so a branch whose events never reach the runner is a branch with no metering: an analyst could burn its `max_turns` ten times over and the meter would never see a token. Fixed by the same rewrite rather than documented as a limit. (Recorded here because it is the second time the same seam has surprised the plan: W1.2's own finding was that attribution is `Event.Author`, not `Branch`.)
>
> **(d) The resume guard the shape appeared to need is dead code.** `fan_out` was written with a `ctx.ResumedInput(SynthesisInterruptID)` check in front of the analysts, on the reasoning that a resumed run must not re-run the expensive part. Instrumenting entry counts showed `fan_out` is entered **once** across a run *and* its approval turn: ADK routes a resumed response to the asker, and nodes upstream of the asker are not re-entered. It holds across a process restart too — kill the daemon at the gate, start a fresh one on the same session DB, `POST /resume`, and the merged result comes back with `reported:4` and the operator's verdict, because run state is reconstructed from the event log and (per finding (a)) the branches' events are now in it. The guard and its state stash were deleted; `synthesize`'s `ResumedInput` check stays, because *that* node is the asker and is re-entered. `TestFanoutResumeKeepsTheFindings` pins the behaviour rather than the guard.
>
> **(e) Fan-out forces a workload to inventory its read-only tools by name.** Under default-deny-unknown, an analyst that names an MCP server without enumerating tools has been granted mutating tools — whether or not any exist on that server today. Refusing that is the intended cost, but it means a fan-out bundle cannot be written without `tool_catalog.tools[].mutating: false` entries for every read tool the roster uses. ADK's own `filterToolsets` is open by default, so nothing below mast would have caught it.
>
> **(f) The shipped anchor roster cannot be a fan-out roster.** `gke-triage`'s specialists hold `patch_resource`: it is a *remediation* roster, and every fan-out branch runs before the one approval gate. Rather than weaken the check or split the anchor bundle mid-release, W3 ships a second example — `examples/workloads/ns-audit`, four read-only namespace analysts plus `_synthesis` — and keeps gke-triage as the refusal case in `U-fanout/C`.
>
> **(g) `request_operator_input` passes the read-only check and still cannot be in a branch.** `effects.NewPredicate` classifies it read-only, correctly — it changes nothing in the world. But a branch is a nested workflowagent with its own scheduler, so an interrupt raised inside one is that scheduler's to resolve and the outer graph has no pause to record. An analyst holding it could park a run that nothing can un-park. Refused by name at construction, with the reason in the message.

### W7.0 — The change-set producer *(mast; added 2026-08-14 by W2 finding (c); blocks W7)*

W7 mints grants bound to exact normalized `(tool, arguments)` signatures. It is a **consumer** of a typed change set, and no workstream produces one — which is the same hole W2 finding (c) fell into from the other side. Today a diagnosis ends in `recommended_actions: array<string>`, so the only thing a diagnoser can hand an executor is prose.

Make the diagnosis emit the change. `finding.json` gains a `proposed_change`: a typed, possibly empty list of `(tool, arguments)` entries drawn from the workload's own `tool_catalog`, validated against the named tool's input schema at the moment the finding is returned — the same check W2.5 already runs on an operator's `edit` args, applied one step earlier. A diagnoser that cannot name a machine-executable change returns none and says why in `escalate`, which is the honest outcome for "raise the memory limit, but I don't know to what".

Everything downstream then stops being prompt-shaped:

- the graph edge becomes a **structural predicate** — *finding carries a non-empty `proposed_change` ∧ the operator's verdict approved it → `change-executor`* — rather than an instruction a model may ignore. `change-executor` stops being an orphan node without anyone writing "please remediate" into a system prompt.
- the operator approves **the object that fires**. Today the finding they see and the call the executor would derive are different artifacts; a typed proposal collapses them into one, which is also what makes W7's freshness bound and precondition re-check meaningful — you cannot re-check a precondition on a paragraph.
- W7 gets its input, and its "legibility rule" (narrow named tools only) becomes checkable rather than aspirational.
- W8's highest-signal example — *"human edited 10 replicas → 4"* — becomes a diff over typed arguments instead of prose scraping.

*Exit:* a diagnosis specialist returns a finding whose `proposed_change` names a tool in the catalog with schema-valid arguments; the executor runs **that** call and no other, or runs nothing when the list is empty; a finding whose `proposed_change` names an unknown tool or invalid arguments is rejected back to the specialist, not passed on.
*Test:* `U-proposed-change` (producer contract + the refusal), and an extension of `U-gate-percall` proving the parked call's signature is byte-identical to the approved finding's `proposed_change`.

### W7 — `per_change_set` *(mast; gated on W2 UAT green **and W7.0**)*

Durable minted-not-chosen grants on the resume-token pattern, consumption paired against the outbox record, plus the freshness bound and precondition re-check the approval window demands, plus the legibility rule.
